CattleFeedAI — Milestone 10 (M10): Notifications & Alerts Summary
================================================================================

1. OBJECTIVE
--------------------------------------------------------------------------------
Implement a robust, secure, and production-ready in-app Notifications & Alerts
workflow for CattleFeedAI, building directly upon Milestones M1 through M9.
The workflow alerts dairy farmers to actionable and critical herd events:
- Feed quality hazards (e.g. UNSAFE feed/silage assessment)
- High-level risk indicators (e.g. HIGH risk assessment)
- Urgent rule-derived management advisories (e.g. Priority.HIGH advisories)
The alerts are persisted in MySQL, presented dynamically on the farmer's mobile
dashboard and dedicated alert inbox, and tracked through read/unread state.


2. ARCHITECTURE
--------------------------------------------------------------------------------
The Notifications & Alerts system operates as an integrated communication and
presentation layer that cleanly consumes events from existing domain services:

  [Existing Assessment / Advisory Event]
         │ (QualityAssessmentService / RiskAssessmentService / AdvisoryService)
         ▼
  [AlertService.processAssessmentAlerts / createAlert]
         │ (Deduplication + Severity mapping + Association)
         ▼
  [MySQL 8+ `alerts` Table Persistence]
         │
         ├───▶ GET /api/alerts/unread-count ──▶ Dashboard 🔔 Indicator Badge
         │
         ├───▶ GET /api/alerts ───────────────▶ AlertListScreen (Filter All/Unread/Read)
         │
         ├───▶ GET /api/alerts/{id} ──────────▶ AlertDetailsScreen (Action details & safety)
         │
         ├───▶ PUT /api/alerts/{id}/read ─────▶ Mark individual alert read
         │
         └───▶ PUT /api/alerts/read-all ──────▶ Mark all unread alerts read for farmer


3. BACKEND IMPLEMENTATION
--------------------------------------------------------------------------------
- Entity Reuse & Schema Validation:
  * Reused existing `Alert` entity (`com.cattlefeedai.api.entity.Alert`) from M1.
  * Added optional, non-breaking entity linking fields: `relatedEntityType` (VARCHAR 50)
    and `relatedEntityId` (BIGINT).
  * Preserved existing enums: `AlertType` and `Severity`. Adjusted MySQL severity column
    definition to safely store full Java enum values: INFO, NORMAL, WARNING, HIGH, CRITICAL.

- Repository (`AlertRepository`):
  * `findByUserIdOrderByCreatedAtDesc(Long userId)`
  * `findByUserIdAndIsReadFalse(Long userId)`
  * `countByUserIdAndIsReadFalse(Long userId)` (O(1) aggregate count)
  * `existsByUserIdAndRelatedEntityTypeAndRelatedEntityIdAndTitle(...)` (atomic deduplication)
  * `markAllAsReadForUser(@Param("userId") Long userId)` (atomic bulk update)

- Service (`AlertService`):
  * `getAlerts()`: Fetches alerts for authenticated farmer in reverse chronological order.
  * `getAlertById(Long id)`: Fetches alert, enforcing 403 ownership and 404 existence.
  * `getUnreadCount()`: Fetches unread alert count for dashboard badge.
  * `markAsRead(Long id)`: Validates ownership (403 if not owner), marks read, persists.
  * `markAllAsRead()`: Atomically marks all unread alerts for the current farmer as read.
  * `createAlert(...)`: Safe alert creator with event deduplication.
  * `processAssessmentAlerts(...)`: Consumes assessment results and generates alerts:
      - QualityStatus.UNSAFE -> AlertType.FEED_QUALITY/SILAGE_QUALITY, Severity.CRITICAL
      - RiskLevel.HIGH -> AlertType.HEALTH_RISK, Severity.HIGH
      - Priority.HIGH Advisories -> Corresponding AlertType, Severity.HIGH

- Controller (`AlertController`):
  * Exposed REST endpoints under `/api/alerts` with OpenAPI / Swagger annotations.
  * Integrated with `AssessmentController` and `AdvisoryService` for automatic triggering.

5. API ENDPOINTS
--------------------------------------------------------------------------------
GET  /api/alerts              - Retrieve farmer's alerts (ordered by createdAt DESC)
GET  /api/alerts/{id}         - Retrieve specific alert (403 for cross-owner, 404 if missing)
GET  /api/alerts/unread-count - Retrieve count of unread alerts for authenticated farmer
PUT  /api/alerts/{id}/read    - Mark specific alert as read (403 for cross-owner)
PUT  /api/alerts/read-all     - Mark all unread alerts as read for current farmer


6. ALERT-GENERATION FLOW
--------------------------------------------------------------------------------
1. Farmer records a TestResult or ingests Visual Screening.
2. Farmer or system calls `POST /api/assessments/test-results/{testResultId}`.
3. Existing `QualityAssessmentService` and `RiskAssessmentService` evaluate parameters.
4. If QualityStatus == UNSAFE:
   -> AlertService generates CRITICAL severity alert.
5. If RiskLevel == HIGH:
   -> AlertService generates HIGH severity alert.
6. If any generated Advisory has Priority.HIGH:
   -> AlertService generates HIGH severity alert.
7. Alerts are deduplicated against existing database entries for that entity and title.
8. Alerts are committed to MySQL with foreign key to farm owner.
9. Dashboard immediately reflects incremented count via `GET /api/alerts/unread-count`.


7. SECURITY & ACCESS CONTROL
--------------------------------------------------------------------------------
- Unauthenticated requests to `/api/alerts/**` return HTTP 401 Unauthorized via Spring Security.
- Farmers can only access and modify their own alerts; queries strictly filter by `user.id`.
- Cross-owner access (`GET /api/alerts/{id}` or `PUT /api/alerts/{id}/read` for another farmer's
  alert) immediately throws `ResourceOwnershipException`, returning HTTP 403 Forbidden.
- Non-existent alerts throw `ResourceNotFoundException`, returning HTTP 404 Not Found.
- Alerts belonging to one farmer are never exposed or leaked in another farmer's list or count.


8. SCIENTIFIC SAFETY & DISCLAIMERS
--------------------------------------------------------------------------------
- Notifications and alerts serve strictly as a communication and workflow presentation layer.
- No new scientific thresholds or diagnostic claims are introduced.
- Strict disclaimers preserved across alert details and presentation:
  "Notifications and alerts are communication and screening tools. They do not constitute
  veterinary medical diagnoses. For clinical herd issues, always consult a certified
  Veterinarian or Veterinary Nutritionist."
- Non-diagnostic terminology strictly maintained: veterinarians are never called "dieticians",
  only "Veterinarian", "Veterinary Nutritionist", or "Animal Nutrition Expert".

10. KNOWN LIMITATIONS
--------------------------------------------------------------------------------
- Alerts currently require polling/refresh (screen focus and pull-to-refresh) within
  the mobile application; push notifications and webhooks are not part of M10.
- Alert generation triggers during explicit assessment evaluations or advisory generation;
  background cron schedulers are omitted per architectural guidelines.


11. FUTURE SCOPE
--------------------------------------------------------------------------------
The following features are intentionally out of scope for M10 and reserved for future milestones:
- Push notifications (Expo Notifications, FCM, APNs)
- SMS, email, and WhatsApp dispatch infrastructure
- Background automated scheduled tasks / crons
- Offline local caching and offline-first queueing
- NIR sensor instrumentation & IoT direct ingestion
